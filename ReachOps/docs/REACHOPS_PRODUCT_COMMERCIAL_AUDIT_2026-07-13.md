- 审计日期：2026-07-13
- 审计基线：`main@0c6d6e503b9c29653ddda131384d93fc9bc3a564`
- 审计角色：产品经理 / 商业化验收负责人
- 审计范围：产品定位、市场适配、功能闭环、应用与数据架构、运行稳定性、安全与合规、工程治理、商业化能力、试点与正式发布验收
- 结论适用范围：基于当前仓库、仓库内审计材料、最新提交状态与可见 GitHub 治理信息；不替代独立安全测试、平台法律意见或真实客户验证

## 1. 执行结论

**ReachOps 当前可以定义为“受控试点阶段的本地社媒意图获客执行内核”，不能定义为已完成商业化验收的获客软件。**

项目在执行计划、状态机、风险门、证据包、失败恢复、本地隐私和默认不提交等方面已经建立了正确的工程骨架；但当前真实环境仍被可用账号与登录态阻塞，没有形成可复核的真实获客结果，GitHub 上也没有持续集成、PR 审核和 Issue 治理证据。商业化所需的租户、账号体系、权限、计费、授权服务、CRM、遥测、客户支持、数据治理和版本运营能力尚未形成完整闭环。

因此，本次审计给出以下发布判定：

| 判定对象 | 结论 |
|---|---|
| 内部开发演示 | 有条件通过 |
| 受控无提交试点 | 有条件通过，必须使用真实可用账号池 |
| 小范围人工授权付费试点 | 暂不通过，需完成 P0 门槛 |
| 可复制商业交付 | 不通过 |
| GA 正式商用 | 不通过 |

建议总体就绪度：**42/100（Controlled Alpha）**。

| 维度 | 分数 | 主要判断 |
|---|---:|---|
| 市场需求与问题价值 | 72 | 评论与社媒互动中的购买意图识别是真实痛点 |

| MVP 功能闭环 | 66 | 计划、采集、评分、队列、执行、证据结构较完整，但真实闭环未成立 |
| 架构完整性 | 58 | 领域骨架较全，商业控制面、渠道抽象和数据治理不足 |

## 2. 产品定位审计

### 2.1 与历史目标的匹配度

历史目标的优先级是：

1. TikTok 评论场景获客：从互动人群识别意向线索，并推进到可跟进对象；
2. 外贸 B2B 邮件自动化；
3. SEO / 广告自动化；
4. 目标客户包括 TikTok Shop 卖家、跨境独立品牌、工厂转 DTC 与外贸团队，重点品类包括宠物、汽配、家居收纳、美妆、健身、小家电等。

当前实现对第 1 项投入最深，对第 2、3 项尚未形成同等级模块。因此，若继续以“全渠道获客软件”对外定位，会产生承诺与交付能力不一致；若收窄为“TikTok 社媒意图雷达 + 人工授权的本地执行工作台”，产品与架构匹配度明显提高。

### 2.2 推荐定位

**推荐一句话定位：**

> ReachOps 是面向跨境电商与外贸增长团队的社媒意图雷达和销售执行工作台：从公开互动中发现高意向信号，形成可解释线索，经过人工审批后进入合规跟进，并用证据链衡量从互动到商机的转化。

不建议使用以下定位作为当前销售承诺：

- 全自动 TikTok 群控获客；
- 无人值守批量评论、关注、私信；
- 全渠道一体化获客平台；
- 已验证稳定出单；
- 可规避平台风控。

### 2.3 首个可销售 ICP

建议首批只服务一个窄 ICP：

- 5–50 个受控业务账号或浏览器配置档案；
- 每周有持续 TikTok 内容和评论互动；
- 已有人负责销售跟进，但线索发现与筛选效率低；
- 能提供清晰产品、地区、语言、负面词、配额和人工审批规则；
- 接受“先发现与排序、后人工确认执行”，而非追求无审核群发。

优先试点行业：宠物用品、汽配、家居收纳。它们与历史目标一致，需求表达相对明确，也便于建立人工标注集和购买意图词典。

## 3. 当前架构的有效部分

### 3.1 正确的产品骨架

仓库已建立以下高价值能力：

- `PRODUCT_ARCHITECTURE.md` 将 AI 限定在计划与辅助判断，执行阶段由确定性本地程序完成；
- `execution_plan.py` 提供目标、配额、模式、风险策略和运行时契约；
- `run_session.py` 建立运行状态机、检查点、暂停、恢复、阻塞与降级状态；
- `page_state_detector.py` 与 `repair_policy_engine.py` 对页面异常和恢复策略建模；
- `risk_gate.py`、`authorization_gate.py` 与 Web 端启动门禁阻止未授权提交；
- `evidence_bundle.py`、截图和 sidecar 形成可审计证据；
- `intelligence/storage.py` 已覆盖内容、候选用户、意图、线索、动作队列、账号健康、活动、配额、执行与事件；
- 本地运行和默认不提交降低了早期数据外泄与误操作风险。

这些能力适合作为未来“渠道连接器执行内核”，不应推倒重来。

### 3.2 正确的产品原则

以下原则建议保留为不可回退约束：

1. 默认 `no-submit`；
2. 真实动作必须有人类授权、配额和可追溯原因；
3. 登录失效、验证码、未知页面状态必须停止，不绕过；
4. 每个真实成功动作必须有截图、结构化 sidecar 和幂等键；
5. AI 不能成为实时执行的单点依赖；
6. 账号健康、冷却、失败切换和重复联系防护必须高于吞吐量；
7. 业务结果必须回写到线索和活动，而不是只记录“脚本执行成功”。

## 4. 关键缺口与风险

### 4.1 P0：真实价值闭环尚未成立

仓库内的真实压力审计显示：

- ixBrowser 可以连接，但抽样配置档案不可用、未登录或超时；
- 真实流程未产生可验证的线索、有效动作或提交成功；
- 99 个候选用户、198 个动作等结果来自 fixture / dry-run；
- 当前客户端状态仍为 `blocked_by_accounts`；
- Windows 当前工作区缺少可作为最终交付证据的完整安装包与本机验收材料。

**影响：** 产品当前证明了“程序可以组织一次获客流程”，但尚未证明“客户可以稳定获得可跟进商机”。

### 4.2 P0：工程治理缺失

截至审计时：

- GitHub 无 PR；
- GitHub 无 Issue；
- 最新提交无状态检查、无工作流运行；
- 最新一次重构同时影响百余个文件；
- 仓库内历史记录显示曾执行 435 个测试，其中 6 个失败、4 个错误，主要集中在 `/api/start` 契约不一致；
- `requirements.txt` 使用下限版本且无锁文件，`pyproject.toml` 不存在。

**影响：** 不能证明最新主分支可重复构建、可回归或可安全发布。

### 4.3 P0：平台依赖与商业连续性风险

当前核心能力依赖 ixBrowser、Selenium、DOM 结构、账号登录态和平台页面行为。该路线可用于受控本地辅助执行，但存在以下风险：

- DOM 变化会直接破坏采集和动作；
- 账号池质量成为系统吞吐的首要瓶颈；
- 公开评论发现与冷启动触达不等于平台授权的商业消息能力；
- 自动评论、关注或私信可能触发平台限制，并影响客户账号资产；
- 如果把浏览器自动化作为唯一渠道，商业收入会与平台变化高度绑定。

**要求：** 把浏览器执行定义为可替换连接器，不得成为领域模型、计费模型或客户数据模型的中心。

### 4.4 P0：授权与更新安全不足

当前本地授权与更新机制适合内部测试，不适合正式收费：

- 授权状态读取本地 JSON 缓存，客户端未见对服务端签名载荷的密码学验证；
- 开发态存在无授权状态时的旁路逻辑；
- 设备标识可通过环境变量覆盖；
- 更新器校验安装包 SHA256，但未见对更新清单进行数字签名；
- 更新清单允许 `http://`；
- 未见在线撤销、离线宽限、并发设备限制、授权审计和篡改告警的完整闭环。

### 4.5 P0：数据治理与隐私能力不足

`intelligence/storage.py` 以单机 SQLite 为核心，使用 WAL 和 busy timeout 是合理起点，但目前存在：

- 单文件存储模块超过两千行，领域、查询、迁移和报表职责混合；
- 通过 `_ensure_columns` 和 `ALTER TABLE` 做渐进变更，未见版本化迁移框架；
- 未见自动备份、恢复演练、加密密钥管理、数据保留期限和客户删除流程；
- 未见租户、工作区、成员、角色、授权主体与数据归属模型；
- 线索与公开用户信息可能构成个人数据，但未形成同意、用途、导出、删除、审计和地区策略。

### 4.6 P1：应用架构可维护性不足

主要信号：

- Web UI、原生客户端、证据包、AI 控制台和存储模块出现 1,000–2,900 行级大文件；
- `tools/reachops_web_ui.py` 混合内嵌 HTML/JS、HTTP 路由、进程管理、缓存、业务校验与日志解析；
- 存在 root 与 `workbench` 下同名的页面状态和修复策略模块，容易产生行为漂移；
- Web 运行态依赖模块级全局变量和单活动进程，限制并发、隔离和测试；
- `run_session.py` 中存在不可达的重复 `return`，表明重构后仍有清理缺口；
- 文档要求过期缓存不能作为启动依据，但 Web 组校验逻辑存在使用缓存组继续通过的分支，需要统一契约。

### 4.7 P1：商业控制面缺失

当前代码与数据模型未形成以下正式商用能力：

- organization / workspace / user / role / seat；
- 订阅、账单、支付、发票、优惠、试用、用量和套餐；
- 服务端 entitlement、授权撤销和设备管理；
- CRM 双向同步、Webhook、API key 和外部集成；
- 客户级功能开关、限额、审计日志和支持诊断；
- 产品遥测、崩溃报告、版本采用率和漏斗分析；
- 客户 onboarding、模板库、帮助中心、状态页和 SLA；
- 业务结果归因：回复、有效对话、会议、报价、订单和收入。

## 5. 推荐目标架构

不要把当前单机客户端直接扩成一个更大的单体。建议形成“五层架构”。

### 5.1 体验层

- Operator Console：目标、活动、线索、审核、执行、异常和证据；
- Team Inbox：统一查看评论、消息、跟进任务与负责人；
- Admin Console：成员、账号、授权、套餐、数据策略与审计；
- Onboarding：行业模板、账号健康检查、首次价值引导。

### 5.2 商业控制面（新增）

建议独立服务或模块：

- Tenant / Workspace / RBAC；
- Subscription / Metering / Entitlement；
- Feature flags / Remote config；
- Device registration / License signing / Revocation；
- Product telemetry / Crash reporting / Support bundle；
- CRM / Webhook / API credentials；
- Compliance policy / Consent / Retention / Deletion。

控制面只保存必要的账户、配置、计量和聚合事件；敏感采集内容可继续本地优先。

### 5.3 领域核心

将当前模型整理为稳定边界：

- Signal：来源、内容、评论、购买意图与可解释特征；
- Lead：主体、资格、优先级、状态、负责人和去重键；
- Campaign：目标、市场、语言、产品、配额和策略；
- Action：建议动作、审批、幂等、执行、结果和重试；
- Evidence：输入、决策、页面状态、截图、sidecar 和摘要；
- Outcome：回复、对话、会议、报价、订单和收入。

### 5.4 渠道连接器层

统一接口，不让领域逻辑直接依赖 TikTok DOM：

- `discover_signals()`
- `collect_interactions()`
- `resolve_identity()`
- `propose_action()`
- `preflight_action()`
- `execute_authorized_action()`
- `capture_evidence()`
- `sync_outcomes()`

连接器优先级：

1. 官方授权的 owned-account 入站互动与业务消息能力；
2. 本地浏览器辅助发现与人工授权动作；
3. CRM / 邮件连接器；
4. 后续 SEO / 广告信号连接器。

### 5.5 本地执行与数据层

保留当前 ExecutionPlan、RunSession、RiskGate、EvidenceBundle，但完成：

- 版本化数据库迁移；
- 存储 repository 分层；
- 加密备份与一键恢复；
- 每工作区独立数据边界；
- 可重放事件与幂等执行；
- 连接器契约测试；
- 明确的 PII 字段目录和生命周期。

## 6. 商业化北极星指标与漏斗

### 6.1 北极星指标

**每周被销售人员接受、来源可追溯、且进入有效跟进的“合格商机数”（Weekly Accepted Qualified Opportunities, WAQO）。**

不能使用以下指标作为商业成功替代：

- 抓取评论数；
- AI 打分次数；
- 浏览器打开次数；
- 已排队动作数；
- dry-run success；
- 截图数量。

### 6.2 核心漏斗

`有效来源 -> 可采集互动 -> 可识别主体 -> 高意向信号 -> 去重线索 -> 人工接受 -> 授权触达 -> 回复 -> 有效对话 -> 会议/报价 -> 订单`

每一层必须同时记录数量、转化率、耗时、失败原因、成本和证据链接。

### 6.3 必须上线的指标

| 层级 | 指标 |
|---|---|
| 激活 | 首次完成配置时间、首次发现高意向线索时间、首周达到价值比例 |
| 质量 | 高意向 Precision、Recall、人工接受率、重复线索率、误报率 |
| 执行 | 账号可用率、页面识别率、预检通过率、授权动作成功率、未知状态率 |
| 风险 | 未授权提交数、重复触达数、验证码绕过数、账号限制率、PII 事件数 |
| 商业 | WAQO、回复率、有效对话率、会议/报价率、订单归因率、每商机成本 |
| 留存 | W1/W4 活跃、活动复用率、席位使用率、付费续费率、流失原因 |
| 运营 | 崩溃率、启动成功率、任务完成率、MTTR、版本采用率、支持工单率 |

## 7. 分阶段商业化验收方案

所有门槛必须采用真实环境和可审计样本。fixture 只能证明代码路径，不能证明市场效果。

### G0：定位与合规边界冻结

**目标：** 确定卖给谁、解决什么问题、哪些动作允许自动化。

通过条件：

- ICP、核心场景、首批国家/地区、语言与行业完成书面冻结；
- 明确 owned-account 入站、公开信号发现、人工授权外联三类能力边界；
- 产品条款、隐私政策、数据处理说明、可接受使用政策和风险披露完成评审；
- 不对外承诺绕过平台限制或无人审核群发；
- 北极星指标与结果归因字段进入数据模型。

失败即停止收费试点。

### G1：工程基线与发布门禁

**目标：** 每次提交可重复验证。

通过条件：

- 主分支保护开启，禁止直接推送；
- 所有变更通过 PR，至少 1 名 reviewer；
- GitHub Actions 执行语法检查、全量单元测试和 Windows 目标环境测试；
- 全量测试连续 10 次通过，失败/错误为 0；
- 依赖锁定并具备漏洞扫描与许可证清单；
- 每个发布生成版本、commit、校验值、安装包和回滚说明；
- P0 缺陷为 0，P1 缺陷有明确豁免人与截止日期。

### G2：真实环境无提交闭环

**目标：** 证明真实账号和真实页面下可以稳定发现、筛选和形成线索，但不执行外联。

建议样本：

- 3 个行业；
- 6–10 个试点客户或内部业务单元；
- 至少 30 个经过人工验收的账号配置档案；
- 至少 1,000 条人工标注评论；
- 至少 100 次完整运行。

通过条件：

| 指标 | 最低门槛 |
|---|---:|
| 客户端启动成功率 | ≥ 99% |
| 合格账号打开并进入目标页 | ≥ 90% |
| 已验收账号登录就绪率 | ≥ 85% |
| 目标页面状态识别率 | ≥ 95% |
| 评论采集与人工抽样一致率 | ≥ 95% |
| 主体去重准确率 | ≥ 99% |
| 高意向 Precision | ≥ 75% |
| 高意向 Recall | ≥ 60% |
| 人工接受率 | ≥ 50% |
| 未知状态后错误继续执行 | 0 |
| 未授权提交 | 0 |
| 证据包完整率 | 100% |

### G3：受控真实动作试点

**目标：** 证明人工审批后的少量动作可控、可回滚、可归因。

前置条件：G0–G2 全部通过。

建议范围：

- 仅允许书面批准的账号、国家、时段、动作和模板；
- 每客户每日动作上限从 5–10 次开始；
- 先 owned-account 入站回复，再扩展其他动作；
- 每个动作必须逐条或批次人工授权；
- 至少 300 个授权动作，持续 4 周。

通过条件：

| 指标 | 最低门槛 |
|---|---:|
| 预检通过后的执行成功率 | ≥ 85% |
| 成功动作截图 + sidecar 完整率 | 100% |
| 幂等冲突 / 重复触达 | 0 |
| 超配额执行 | 0 |
| 未授权执行 | 0 |
| 验证码或登录异常绕过 | 0 |
| 账号受限率 | ≤ 1%，且每例有 RCA |
| 人工暂停生效时间 | ≤ 5 秒 |
| 严重故障证据与复盘完成率 | 100% |

### G4：付费试点与单位经济验证

**目标：** 证明客户愿意付费，且结果价值高于交付成本。

建议：6–10 个付费客户，连续 8 周；至少 3 个客户完成续费意向确认。

通过条件：

- 试点客户激活率 ≥ 70%；
- 首次价值时间中位数 ≤ 30 分钟；
- W4 核心功能活跃率 ≥ 60%；
- 人工接受的合格商机中，至少 10% 进入有效对话；
- 至少 3 个客户能提供可核验的会议、报价或订单归因；
- 每客户月支持工时中位数 ≤ 3 小时；
- 软件毛利假设 ≥ 70%，含第三方、支持和基础设施成本；
- 试点转正式付费意向 ≥ 50%；
- 无重大数据、安全或平台合规事件。

价格只作为实验，不作为既定事实：

- Assisted Pilot：¥2,999–5,999 / 月，含 onboarding、有限账号位和人工支持；
- Growth：通过试点后按账号位 + 活跃合格线索或工作区计费；
- Agency / Enterprise：按工作区、席位、连接器、支持等级和合规需求报价。

计费不建议绑定 AI token、抓取评论数或点击次数；优先绑定“账号位、席位、活跃合格线索、连接器和服务等级”。

通过条件：

## 10. 最终验收规则

商业化验收不是“页面齐全”“脚本跑完”或“fixture 压测通过”。最终签字必须同时满足：

1. **可卖：** ICP、价值、价格和风险承诺清楚；
2. **可用：** 真实客户能在 30 分钟内获得第一批可接受线索；
3. **有效：** 线索能进入回复、对话、会议、报价或订单；
4. **稳定：** 版本可重复构建、测试、升级、回滚和恢复；
5. **安全：** 未授权动作、重复触达、数据泄露和绕过行为为零；
6. **可运营：** 能计费、授权、撤销、监控、支持和定位问题；
7. **可扩展：** TikTok 浏览器自动化只是连接器之一，不是整个产品架构；
8. **可审计：** 每个结论都有真实运行证据、客户样本和责任人。

在 G4 通过前，产品对外状态应统一标记为：**Paid Pilot / Controlled Beta**，不得标记为 GA。
